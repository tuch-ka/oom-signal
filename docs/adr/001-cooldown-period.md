# ADR-001: Cooldown-период для сигнала о превышении порога памяти

## Статус

Принято

## Контекст

oom-signal отправляет сигнал процессу по rising edge — при переходе потребления памяти через порог. Если usage осциллирует вокруг порога (типичный сценарий: GC освобождает память, аллокации продолжаются), каждый переход генерирует новый rising edge, и сигналы отправляются безостановочно.

Интегратор сообщил: «сигналы отправлялись безостановочно».

## Рассмотренные варианты

### 1. Cooldown-период (фиксированный)

После отправки сигнала следующие сигналы подавляются в течение N секунд, независимо от состояния exceeded.

- Простая реализация и понятный контракт: «не чаще чем раз в N секунд»
- Легко настраивать и объяснять интегратору
- Не требует изменения семантики порога

### 2. Гистерезис (разные пороги входа/выхода)

Сигнал отправляется при превышении верхнего порога, exceeded сбрасывается только при падении ниже нижнего порога.

- Исключает осцилляцию от малых колебаний вокруг одного порога
- Сложнее настраивать: нужно задавать два значения вместо одного
- Сложнее объяснять интегратору: «почему сигнал пришёл при 85%, а не при 80%?»
- Не решает проблему полностью: при колебаниях между нижним и верхним порогом осцилляция сохраняется

### 3. Координированный cooldown + гистерезис

Комбинация обоих подходов.

- Максимальная защита от осцилляции
- Избыточная сложность для демона мониторинга
- Два настраиваемых параметра вместо одного

## Решение

Фиксированный cooldown-период: **5 секунд** по умолчанию.

Флаг `--cooldown` с значением по умолчанию `5s`, минимум `0` (отключён).

## Обоснование выбора значения

- **GC-осцилляция**: типичный период 1–3 секунды. 5с перекрывает с запасом.
- **Реакция приложения**: обработчики сигнала обычно укладываются в 1–5 секунд (flush, cleanup, graceful shutdown). Если за 5 секунд приложение не отреагировало — повторная отправка того же сигнала не поможет.
- **Быстрый рост к OOM**: при росте 100 МиБ/с на контейнере с 2 ГиБ свободной памяти OOM kill произойдёт через ~20 секунд. 5с молчания — четверть времени, 10с — половина. 5с — приемлемый баланс.
- **Согласованность с poll interval**: 5с = 50× default poll interval (100мс). Достаточно, чтобы не пропустить реальный rising edge после recovery.

## Последствия

- Сигнал отправляется не чаще одного раза в 5 секунд (по умолчанию)
- Интегратор может увеличить или уменьшить cooldown через `--cooldown`
- При `--cooldown=0` поведение возвращается к текущему (rising edge без ограничений)
- Rising edge остаётся основным механизмом: cooldown лишь ограничивает частоту отправки
